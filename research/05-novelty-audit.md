# Prior Art Review: UPL's Four-Property Combination

*An adversarial audit: the researcher was instructed to find the thing
that already does this, not to flatter the project.*

UPL's combination of properties, assessed against each candidate:

1. One declarative bundle file describes a whole app: schema, actions
   with requires/ensures contracts, queries, UI.
2. A **deterministic** compiler (not an LLM) unpacks it into runnable
   code; sha256 of canonical form is the program identity; drift is
   detectable (`uplc verify`).
3. The bundle carries its own acceptance tests, executed by the
   toolchain against the generated app; contracts are runtime-enforced.
4. The intended author is an LLM (zero training data, authored from a
   guide in context), and language evolution is driven by agent
   failure reports.

## Findings by project

**Wasp (wasp-lang) + MAGE.** Wasp is a real DSL (`main.wasp`, recently migrated to a TypeScript-embedded spec as of June 2026) that a genuine compiler unpacks into React + Node.js + Prisma code — this is the field's best example of property 2's "one source → multiple real targets" shape, and its compiler is a conventional deterministic build tool (same input, same output), not an LLM. But it has no contract language (no `requires`/`ensures`), no acceptance tests bundled with the spec and executed against the generated app by the toolchain, and — crucially — it is explicitly *not* designed for LLM authorship: it was built for humans, and its June 2026 move away from a custom DSL toward plain TypeScript was driven by developer complaints, moving it further from "designed for machine authorship, zero training data." MAGE (Mage/"Wasp AI") uses GPT only to *produce* a `.wasp` file from a prose prompt one time; it's an LLM-authoring assistant bolted onto a human-oriented DSL, not a language whose evolution is driven by agent failure reports. Shares: 2 (partially). Lacks: 1 (contracts), 3, 4.

**Darklang / Darklang-GPT.** Paul Biggar's team explicitly pivoted the whole platform in 2026 to make AI the primary (possibly only) author of code, redesigning the language/editor/infra trio around trace-driven development and "invisible infrastructure." This is the strongest precedent for property 4's intent (a language whose target author is an LLM). However, it's not a declarative bundle describing schema+actions+contracts+UI in one file compiled deterministically to Python/SQL/HTML — Dark is closer to a live, deployless runtime/editor than a compile-and-verify pipeline, and no evidence surfaced of requires/ensures contracts or spec-bundled acceptance tests checked by the toolchain. Shares: 4 (strongly). Lacks: 1, 2 (as described), 3.

**Amplication.** Model-driven generator: entities defined once, deterministic-ish templates emit NestJS/Prisma/GraphQL/React admin code plus generated unit tests, continuously pushed to a repo. This is a decent analogue for "one spec, whole app, generated tests" but it's schema-centric (not actions-with-contracts or UI-as-spec), has no requires/ensures contract layer, no sha256 program-identity/drift-verify concept, and was never framed as an LLM-authorship language. Shares: fragments of 1 and 2. Lacks: 3, 4.

**Ur/Web and Opa.** Both are academically pedigreed single-language, multi-target compilers (Ur/Web → server binary + JS client + SQL; Opa → Node.js + browser JS, with an automatic client/server "slicer"). These are the strongest historical precedent for "one deterministic compiler unpacks one source into server+client+DB code" (property 2's mechanics, minus the contracts/tests/LLM angle) — Ur/Web even has strong static typing that catches SQL-injection-class bugs, which gestures at contract-like guarantees but is compile-time type safety, not runtime-enforced spec-level requires/ensures, and there's no bundled acceptance-test convention. Both predate LLMs entirely, so property 4 (intended LLM authorship, zero training data) doesn't apply, and neither claims content-hash program identity or spec/code drift verification. Shares: 2 (mechanically, the closest classical precedent). Lacks: 1 (partial), 3, 4.

**Convex.** Markets itself around "deterministic functions" (their term for the query/mutation execution model avoiding races), written in plain TypeScript against Convex's platform APIs, and "generated by AI with good accuracy." This is LLMs writing ordinary TypeScript against a deterministic *runtime*, not a special declarative bundle DSL compiled by a deterministic *compiler* into independently-runnable Python/SQL/HTML artifacts — no schema+actions+contracts+UI single file, no acceptance tests baked into a spec, no sha256/drift-verify story, no claim the language itself is designed for/by LLMs. Shares: essentially none directly (their "deterministic" is a different axis — execution determinism, not spec→code compilation determinism). Lacks: 1, 3, 4.

**Encore.dev.** Infrastructure-from-annotations in ordinary Go/TypeScript; explicitly markets itself (vs. Convex) as *not* requiring a proprietary language so "AI agents work with familiar patterns." This is the opposite bet from UPL on property 4 — it deliberately avoids a bespoke DSL so mainstream LLM training data applies. Shares: none of the four meaningfully.

**Tessl.** The most important conceptual sibling. Tessl's thesis — spec-as-source, code is a regenerable, never-hand-edited artifact, "the spec is the source, the code is the compiled output" — is nearly identical rhetoric to UPL's premise. But per multiple independent reviews (CodeMySpec, Martin Fowler's SDD comparison), Tessl's regeneration engine is closed-beta, JavaScript-only, and **demonstrably non-deterministic**: "running the same spec twice produces different implementations," making it "fully dependent on a non-deterministic compiler." This is exactly the property UPL claims to solve (byte-identical output, sha256 program identity). Tessl also doesn't foreground requires/ensures contracts or a "spec carries acceptance tests the toolchain runs" convention as a load-bearing mechanic, and isn't framed around LLM-native language design with zero training data. Shares: 1 (spec-as-source framing) and aspirationally 3 (regeneration-over-hand-edit). Explicitly lacks: 2 (the crux gap). Ambiguous on 4.

**GitHub Spec Kit / Amazon Kiro.** Both formalize spec→plan→tasks→implementation workflows to structure an LLM coding agent, with Kiro adding requirement-to-task traceability (EARS-format requirements). But in both, the actual code-writing step remains an LLM producing code non-deterministically each run; neither ships a deterministic compiler, a contract runtime, or a hash/verify mechanism for spec-vs-deployed drift. These are process scaffolding for humans directing LLM agents, not compilers. Shares: fragments of 3 (spec discipline, traceability). Lacks: 1 (bundle format is generic markdown/EARS, not a schema+actions+UI language), 2, 4.

**Remy (MindStudio) — the single closest analogue found.** Remy compiles one annotated-Markdown spec (MSFM) into a full multi-interface app: backend methods, typed SQL tables with migrations, auth, frontend, tests, and deployment, marketed explicitly as "the spec is the program, the code is what gets compiled" (property 1, almost exactly). But Remy's own creator states outright, on Hacker News and on their blog: *"TypeScript's compile step is deterministic... Remy's compile step uses an LLM, so the same spec can produce slightly different code on each compile"* — and frames "functionally equivalent" as an acceptable substitute for byte-identical, with a manual "sync button" instead of a hash-based verify/drift command. This is the one property (2) where Remy self-consciously chooses the opposite of UPL's bet. No requires/ensures contract layer or spec-bundled acceptance tests surfaced in the docs reviewed, and the spec is pitched as human/PM-readable prose first, agent-readable second — not an LLM-native language whose evolution is driven by agent failure telemetry. Shares: 1 (closely). Explicitly, admittedly lacks: 2. Lacks/unclear: 3, 4.

**Self-Spec (OpenReview, 2025).** Academic technique where a model authors its own compact spec schema per-problem, then codes only from that confirmed spec, using T=0 (deterministic decoding) to improve HumanEval pass@1. This is model-authored specification improving code-gen reliability, but it's single-function-benchmark scoped, not a full-stack bundle language with schema/actions/UI, has no compiler at all in UPL's sense (still LLM-generates the final code from the spec each time), and "deterministic" here means sampling temperature, not compiled-artifact identity. Shares: a sliver of 3/4 in spirit. Lacks: 1, 2 (no compiler), most of 3.

**Vercel "Zero" / Armin Ronacher's "A Language for Agents."** Zero (May 2026) is a systems language whose entire toolchain — JSON-native compiler diagnostics, capability-based I/O, no English error text — is built for AI agents to read/repair/ship, explicitly solving the "no training data" problem UPL also names as a design constraint (property 4, strong match). But it's a low-level native-binary systems language, not a full-stack schema/actions/queries/UI bundle, has no contracts-as-spec or acceptance-tests-in-bundle convention emphasized, and while its AOT compiler is deterministic in the ordinary sense, that's not marketed as a program-identity/hash/drift-verification feature. Ronacher's essay (Feb 2026) argues for agent-friendly language *design principles* generally but explicitly doesn't propose deterministic-compiler-as-verification, contracts, or a concrete language. Shares: 4 (close on intent, not on domain). Lacks: 1, 2 (different sense), 3.

**"LLM-hardened DSL" framing (Dean Mai, 2025).** A conceptual essay arguing DSLs should be co-designed assuming an LLM co-author, citing Pact and Scilla (formally-verified smart-contract languages) and Langium/NeMo-Guardrails as examples of embedding verification into generation. This is the clearest *articulation* of UPL's philosophy in the abstract, but it's commentary, not a shipped system, and its cited examples (blockchain contract DSLs) are narrow, verification-heavy, human-authored languages — not full-stack app bundles with UI, nor deterministic-compiler-with-hash-identity, nor language-evolves-from-agent-failure-reports. Shares: philosophical alignment only.

## Verdict

**(a) Is UPL's combination novel?** As an exact four-property conjunction, yes — no system found in this search has all four simultaneously. Every individual property has real prior art, but the specific bundling is unclaimed territory in what was found.

**(b) Single closest thing?** It splits by axis. On *shape* (one declarative file = whole app, "spec is the program, code is compiled"), **Remy** is the closest, almost a slogan-match — and it is the most instructive because its creator explicitly names and then rejects UPL's central bet: they use an LLM as the compiler and accept non-determinism as the cost of doing business. On *mechanism* (a real, mature, non-LLM compiler turning one source into multiple real runtime targets), **Wasp** and, historically, **Ur/Web/Opa** are closest. On *intent* (a language meant to be authored by an agent, not a human, addressing the zero-training-data problem), **Darklang-GPT** and **Vercel Zero** are closest. No single project combines the "Remy shape" with the "Wasp/Ur-Web determinism" with the "Darklang/Zero agent-authorship intent" plus runtime contracts and in-spec acceptance tests.

**(c) What differentiation is substantive vs. cosmetic?**
- *Substantive:* Property 2 as UPL states it (a literal deterministic, non-LLM compiler; sha256 program identity stamped into artifacts; a `verify` command for spec/code drift) is the real gap. It is precisely the point on which the most directly comparable current products (Tessl, Remy) explicitly and self-consciously fold — both ship LLM-based regeneration and treat "functionally equivalent, not byte-identical" as an acceptable substitute. Choosing determinism instead of accepting that tradeoff is a genuine, non-cosmetic engineering bet, not marketing language.
- *Substantive:* Property 3's specific combination — contracts that are *runtime-enforced* in the generated code plus acceptance tests that live in the spec and are *executed by the toolchain against the generated app* — wasn't found paired together anywhere. Several tools generate tests (Amplication) or push contract *concepts* (Design-by-Contract is decades old, unrelated to LLM generation), but "spec carries its own tests, machine runs them against what it built, human only reads the spec" as a designed division of labor is uncommon in this exact form.
- *Cosmetic/weakly differentiating:* Property 1 (single bundle file describing schema+actions+queries+UI) is not unique — Wasp, Remy, Amplication, Ur/Web, and Opa all already do "one source, whole app" in some form; this is table stakes in the space, not a differentiator.
- *Real but narrower than it sounds:* Property 4 (LLM as intended author, ~200-line guide, zero training data, language evolves from agent failure reports) is a legitimate and rare framing, but Darklang-GPT and Vercel Zero show the *idea* of agent-native language design is already actively being pursued by well-funded teams in 2026 — UPL isn't the only one to have had this thought, it's just applying it to a different (full-stack CRUD-app) domain than either of those two.

**(d) Novelty confidence: ~65%**, with the uncertainty weighted toward "someone is about to ship the exact combination, if they haven't already." Reasoning: the market is converging on this gap in real time — the loudest criticism of the entire 2026 spec-driven-development wave (Tessl, Remy, Kiro) is precisely "your regeneration is non-deterministic," which is a neon sign pointing exactly at what UPL built. Wasp is actively moving its spec layer around; Remy launched mid-2026 with the "spec is the program" framing already in place; Darklang and Vercel are actively iterating on agent-native language design. Given how fast-moving and crowded this adjacent space is, and given that this search (~14 queries, English-language, no patent search, no academic PL-conference deep dive beyond arXiv hits) was not exhaustive, treat 65% as "probably first to this exact combination today, but the combination is now an obvious-in-hindsight synthesis that the field is visibly circling," not "defensibly unique moat."
