# The Bundled/Unpackable Meta-Language: An AI-Authored "Write Once, Unpack Everywhere" Format

## 1. The concept, stated precisely

The proposal: a single artifact — the **bundle** — in which an AI expresses an entire application (domain logic, UI, data model, infrastructure), and an **unpacker** that compiles/transpiles it into whatever today's runtimes demand: Python for the server, HTML/CSS/JS for the browser, SQL for the database, Terraform/YAML for infra. The premise, following the tweet that inspired this: since AI is the author, human read/write ergonomics stop being a design constraint. The language can be denser, more formal, more redundant, and less pleasant than anything a human would tolerate — as long as it remains *auditable* by some means.

This is not a new dream. It is the Model-Driven Architecture dream, the 4GL dream, and the UML executable-model dream. The interesting question is not "is this a good idea?" (history says: usually not) but "does an LLM author change the specific reasons it failed?" I'll argue it changes about half of them — and introduces new ones.

### What the bundle would contain

A serious design needs at least four layers, because different consumers need different fidelities:

1. **Intent layer** — natural-language rationale, requirements, and *acceptance criteria as executable tests*. This is the layer humans audit and the layer an AI reads to regenerate or repair everything below it. Crucially, intent alone is not a program: it is lossy and ambiguous, which is exactly the problem Tessl-style "spec-as-source" tools are hitting (Fowler's team observed non-deterministic regeneration from identical specs).
2. **Semantic IR** — the actual source of truth. A typed, effect-annotated representation with a **declarative core** (data schema, UI component tree, state machines, workflows, API contracts, permissions) and **imperative escape hatches** (a small, formally-specified expression/statement language for the 10–20% of logic that declarative forms can't express). The MLIR lesson applies directly: don't build one flat IR; build a *stack of dialects* — a schema dialect, a UI dialect, a workflow dialect, a compute dialect — that lower progressively and independently.
3. **Target bindings** — per-target annotations and pinned decisions: "this workflow lowers to a FastAPI endpoint," "this component uses native `<dialog>`," pinned library versions, capability requirements (network, storage). This is where OpenAPI and Terraform are the right analogies: declarative contracts with well-defined lowering, plus a plan/apply step that makes changes inspectable before they land.
4. **Assets and fixtures** — data, seeds, migrations, test vectors, golden outputs. The golden outputs matter more than usual: they are how you verify that two different unpackings mean the same thing.

### How unpacking works

Unpacking should be **progressive lowering, not translation**. The Haxe/Kotlin-Multiplatform experience is instructive: compiling one language to nine targets works well for *pure logic* and falls apart at the *platform seams* — UI, I/O, concurrency, even string/decimal rounding semantics differ across targets. KMP's eventual pragmatic answer (share logic, write UI natively per platform) is a warning: a single imperative language "compiled to everything" re-fights the impedance war on every target.

The bundle sidesteps this by not having one paradigm to force everywhere. HTML's document model vs. Python's imperative model stops being a mismatch if the bundle's UI dialect is *already* a declarative tree (it lowers naturally to HTML/React/SwiftUI) and its logic dialect is *already* an effect-typed workflow graph (it lowers naturally to Python handlers, SQL queries, or JS). The impedance mismatch is a symptom of choosing a general-purpose language as the source; a multi-dialect IR dissolves most of it by construction. What remains — e.g., logic that must run identically on client and server — is best handled by lowering the compute dialect to **WebAssembly**, which by 2025 (Wasm 3.0 ratified, WASI Preview 2, Component Model with WIT interfaces) is a credible "one semantics, every runtime" substrate. A pragmatic UPL might unpack *idiomatic* code where humans might look, and Wasm components where exact cross-target semantics matter.

### Round-tripping edits

This is where MDA died, so it deserves precision. Three regimes, in order of preference:

- **Spec-anchored (no round trip):** unpacked artifacts are marked `GENERATED — DO NOT EDIT` (exactly what Tessl does). All edits happen in the bundle; artifacts are cattle, not pets. Clean, but historically users *always* end up editing output.
- **AI-lifted edits:** when someone (human or agent) patches the generated Python, an AI "decompiles" the patch into a bundle delta, regenerates, and verifies the regenerated output preserves the patch's observable behavior via the golden tests. This was impossible in 2005 — syntactic round-trip tools couldn't reverse-map arbitrary edits — and is merely *hard* now. This is the single biggest thing AI changes.
- **Pinned escape hatches:** edits that can't be lifted get quarantined into named extension points stored verbatim in the bundle, so regeneration re-splices them. This is Terraform's `ignore_changes` / MDA's protected-regions idea, and it must be a last resort because every pinned region is future round-trip debt.

## 2. Prior art: what the graveyard and the survivors teach

**Multi-target languages (survivors, with caveats).** Haxe has quietly shipped to JS, C++, C#, Java, Python, PHP and consoles for 20 years; Nim compiles to C/C++/JS; ClojureScript and KMP thrive. Pattern: they succeed as *shared-logic* vehicles with per-target standard-library shims, and they succeed with *human* maintainers who understand the target. None attempts to emit the whole application including UI, schema, and infra — the UPL's distinguishing (and riskiest) ambition.

**IRs (the strongest technical foundation).** LLVM proved a typed SSA IR can serve dozens of frontends and backends. MLIR proved the more important thing for UPL: *multiple abstraction levels can coexist in one framework*, with dialects lowering progressively and independently. A UPL bundle is best understood as "MLIR for applications": app-level dialects (schema, UI, workflow) above code-level ones. Wasm + WASI + Component Model provide the alternative strategy — don't transpile, ship a universal runtime — and a real UPL would use both.

**Declarative spec formats (the quiet success of the idea).** OpenAPI, Terraform, SQL DDL, GraphQL schemas *are* narrow-domain UPLs: machine-oriented declarative sources from which many artifacts (clients, servers, docs, plans) are deterministically generated, with humans auditing the spec rather than the output. Pandoc is the round-trip analogy: a semantic AST with N readers and writers — and its known lossiness at format edges is a preview of UPL's lossiness at platform edges.

**Model-driven engineering (the graveyard).** MDA/executable-UML failed for reasons worth listing because they are the test the UPL must pass: (1) **round-trip hell** — once developers edited generated code, the model stopped being the master and silently rotted; (2) **leaky abstractions** — UML concepts (associations, statecharts) had no clean mapping to target languages, so generated code was alien and the last 20% required dropping below the model; (3) **the 80% problem** — generation covered the easy majority and the hard minority destroyed the economics; (4) **the model was harder to write than the code**, so the abstraction had negative leverage; (5) organizational factors. Note which of these are about *human* authors and maintainers: most of them.

**AI-era spec-as-source (the current frontier).** GitHub Spec Kit and Amazon Kiro (July 2025) are "spec-first": markdown specs drive generation, then code becomes the maintained artifact. Tessl is the genuinely UPL-adjacent one — "spec-anchored," code marked non-editable, 1:1 spec-to-code mapping — and Fowler's group's critique is the sharpest sentence in this literature: naive spec-as-source risks combining *"the downsides of both MDD and LLMs"* — MDD's rigidity plus LLM nondeterminism. Meanwhile, AI-first language experiments (GlyphLang's token-efficient syntax, Pel for agent orchestration) and verification research (Astrogator's formal query language achieving 83% verification of LLM-generated Ansible; Dafny as a verification-aware intermediate language) sketch the missing piece: making the machine, not the human, the checker.

## 3. What AI actually changes

**Tractable now: the authoring economics.** MDA's fatal asymmetry — the model was harder to write than the code — inverts. An LLM can emit a verbose, formally-annotated, redundant bundle (types, contracts, tests, provenance notes) at near-zero marginal cost. Verbosity and formality, historically adoption-killers, become free. This is the ploeh-blog "design by inconvenience" insight: optimize the language for *verifiability* (refinement types, effect types, contracts) precisely because no human has to endure writing it.

**Tractable now: round-trip and the 80% problem.** Syntactic round-trip tools failed because reverse-mapping arbitrary edits is not a syntactic problem — it's a comprehension problem. LLMs do comprehension. Lifting a hand-patch back into a bundle delta, or writing the ugly 20% inside a typed escape hatch *while keeping it inside the bundle*, is squarely within current model capability, provided there's a verification harness to confirm the lift preserved behavior.

**Should unpacking be deterministic? Yes — and this is the key architectural decision.** It's tempting to say "the unpacker is just an LLM; determinism doesn't matter." It matters enormously: nondeterministic unpacking means every regeneration produces a full-file diff, destroys caching and incremental builds, makes `bundle v1 → v2` code diffs unreviewable, and makes "does the artifact match the bundle?" undecidable. The right split is: **AI at the boundaries, determinism in the middle.** AI compresses intent into the semantic IR (creative, nondeterministic, verified by the test layer); a *conventional deterministic compiler* lowers the semantic IR to targets (boring, cacheable, provable); AI returns only for repair, edit-lifting, and evolving the bundle. The Tessl regeneration-instability finding is empirical support: teams there iterate on specs specifically to *recover* determinism. Don't recover it — design it in.

**New failure modes.**
- **Bundle–artifact drift**: deployed artifacts diverging from the bundle via hotfixes, exactly the model-code drift of MDA, now faster because agents patch code too. Mitigation: artifact hashes recorded in the bundle; CI refuses drift.
- **Intent–IR divergence**: the NL intent layer says one thing, the semantic IR another; humans audit the prose while the machine executes the IR. This is the *new* round-trip hell, one level up.
- **Verification-oracle gap**: if tests are also AI-generated from the same intent, errors correlate. You're verifying the model against itself.
- **Monoculture/provenance risks**: one buggy lowering rule ships the same vulnerability into every target of every app; and a format humans can't casually read is a format where malicious payloads hide more easily. Auditability must therefore be *by construction* — type systems, effect capabilities ("this app cannot open sockets"), property tests, semantic diffs rendered as NL summaries — not by code reading.

## 4. Verdict

**Feasibility: 6/10 in constrained domains within ~5 years; 3/10 as a general-purpose replacement.** Every ingredient exists — MLIR-style layered IR, Wasm as universal runtime, declarative app dialects (React/SwiftUI-like trees, SQL DDL, Terraform), LLMs capable of authoring and lifting edits, nascent verification tooling. Nothing here requires new science. What it requires is the thing MDA never got: an economically sustainable answer to the last 20%, and a trust story for artifacts nobody reads. For CRUD-plus web/mobile applications — schema + workflows + UI + infra, which is a large fraction of all software — a bundle format is genuinely plausible. For kernels, games, novel systems software: no.

**The three hardest problems:**
1. **Semantic equivalence across targets.** Proving that the Python lowering, the JS lowering, and the SQL lowering of one workflow *mean the same thing* (numerics, string semantics, concurrency, error propagation) is the deep compiler problem Haxe never fully solved. Wasm helps for compute; the seams (UI behavior, transaction semantics) remain.
2. **The verification oracle.** The bundle must carry enough independent, executable meaning (contracts, property tests, golden traces) to check both AI authoring above it and lowering below it — without the tests being generated by the same distribution as the code they check.
3. **Governed evolution.** Not one round trip but a lifetime of them: dependency upgrades, platform churn, hand-patches under incident pressure, agents editing at multiple layers concurrently — while keeping the bundle authoritative. This is a version-control and process problem as much as a language problem, and it's where MDA actually died.

**Minimal viable version:** a typed, layered bundle format (call it `.upl`) for one narrow vertical — internal business web apps — containing (a) NL intent + acceptance tests, (b) a semantic IR with schema/workflow/UI dialects plus a small typed expression language as escape hatch, (c) a **deterministic** compiler to exactly two stacks (e.g., FastAPI+Postgres and React, with shared validation logic lowered to a Wasm component), (d) generated code marked non-editable, with an AI "lift" tool that converts hand-patches into bundle deltas and proves behavior preservation against the golden tests, and (e) a semantic-diff tool that renders bundle changes as human-readable summaries. Ship that, survive two years of real maintenance and one framework migration without anyone abandoning the bundle, and the thesis is proven. That last clause is the entire game: MDA demos always worked; MDA *maintenance* never did.
